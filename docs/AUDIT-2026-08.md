# RushRank — Codebase Audit & Roadmap to Multi-Chapter Demos

**Date:** 2026-08-06
**Scope:** full repo — `python_server/`, `frontend/`, `supabase/`, CI/deploy config
**Method:** static read of every route, service, model, migration and page; `pytest` (81 passed), `tsc --noEmit` (clean), `next build` (clean). No live database was available, so DB-dependent claims are derived from comparing SQL in the code against the committed migrations — each one is cited by file and line so you can confirm against production in minutes.

---

## 0. Verdict up front

**You cannot demo this to another fraternity today, and the reason is not polish — it's that the two paths a new chapter would walk down are both severed.**

1. **Self-serve signup does not complete.** `/get-started` sends a Supabase magic link, but nothing in the magic-link flow ever writes `localStorage.access_token`, which is the only token the API client reads. Chapter provisioning 401s, and even if it didn't, the redirect to `/dashboard` bounces to `/login` where the user has no password. A new chapter can only be created by you, by hand, in SQL.
2. **The headline feature is switched off.** Voting and Results are behind `NEXT_PUBLIC_ENABLE_VOTING`, hidden from navigation, and the Results page would show an empty table for every round even if you turned it on — because results are read from a `round_pnms` table that nothing ever writes to.

Underneath both sits one root cause worth naming clearly: **there are two incompatible database schemas in this repo**, `supabase/schema.sql` and `supabase/migrations/`, and the backend code is written against a mix of the two. Most of the `try/except` blocks in `routes.py` exist to paper over that. Every "flaky" bug you've chased is probably a symptom of it.

The good news: the parts that work, work well. Rush Mode, PNM management, events, tags, exports, theming and the entire bid-list backend are real, tested, and shippable. The gap to a credible demo is roughly **3–4 weeks of focused work**, and the first week is almost entirely about the schema and the signup path.

| Area | State |

## 1. Blockers — fix these before any demo

### B1. Self-serve signup never authenticates the new admin
`frontend/components/marketing/SignupWizard.tsx:56-72`

The wizard stores pending chapter details, sends a magic link, and on return calls `provisionChapter(pending)`. That goes through `lib/api.ts`, which reads the bearer token from `localStorage.access_token` (`frontend/lib/api.ts:18-21`). A grep across the whole frontend shows **exactly one place writes that key** — the password login form (`app/login/page.tsx:73`). The magic-link path never does.

Consequences, in order:
- `provisionChapter` sends no `Authorization` header → 401 → the wizard shows "Provisioning failed".
- `router.replace("/dashboard")` → `Protected` (`components/Protected.tsx:9`) finds no token → redirect to `/login`.
- The user signed up with a magic link, so they have no password. Dead end.

**Fix:** derive the token from the Supabase session rather than storing a copy. Replace `getToken()` with `supabase.auth.getSession()` (which also handles refresh — see B2), and add an `onAuthStateChange` listener that keeps `Protected` in sync.

### B2. Sessions expire silently and there is no refresh
`frontend/lib/api.ts:18-21`, `frontend/components/Protected.tsx`

The access token is snapshotted into `localStorage` at login and never refreshed. Supabase access tokens default to a one-hour life. After an hour, every request 401s and the user sees the generic *"Authentication failed (401). Your session may have expired."* string with no automatic recovery — they must log out and back in.

For a live voting session in a chapter meeting, this is the difference between a demo that works and one that dies in front of forty people. Same fix as B1: read from the live Supabase session.

### B3. Voting results are always empty
`python_server/services.py:1534-1536`

```sql
WHERE p.id IN (
    SELECT pnm_id FROM round_pnms WHERE round_id = $1
)
```

Nothing in the codebase ever inserts into `round_pnms`. Rounds carry their PNM list in the `voting_rounds.selected_pnm_ids` array instead (`routes.py:1724`, `routes.py:1894`). So `GET /rounds/{id}/results` returns `[]` for every round, forever. The Results page renders an empty table and the Analytics page's round data is empty too.

**Fix:** either write to `round_pnms` when a round is created, or change the query to `WHERE p.id = ANY(SELECT unnest(selected_pnm_ids) FROM voting_rounds WHERE id = $1)`. Pick one and delete the other — having both concepts is what caused this.

### B4. `PNMWithVotes` is missing four fields, and `BulkArchiveRequest` has them
`python_server/models.py:74-85`

```python
class PNMWithVotes(PNM):
    vote_count: int
    yes_count: int
    no_count: int

class BulkArchiveRequest(BaseModel):
    pnm_ids: List[str]
    archived: bool
    dont_know_count: int      # ← these four belong on PNMWithVotes
    favorite_count: int
    yes_percentage: float
    controversy_score: float
```

This looks like an indentation slip during a merge, and it breaks two things at once:

- **Bulk archive is dead.** `POST /pnms/bulk-archive` now requires `dont_know_count`, `favorite_count`, `yes_percentage` and `controversy_score` in the request body. The PNMs page sends only `pnm_ids` and `archived` (`app/(dashboard)/pnms/page.tsx:230-236`) → **422 on every call**.
- **Results lose their numbers.** `get_round_results` computes all four in SQL (`services.py:1526-1531`) and passes them to `PNMWithVotes(...)`, where Pydantic silently drops them. Even after B3 is fixed, the Results page would show 0% score, 0 favorites and 0 "Unknown" for every PNM.

Moving the four fields up one class fixes both.

### B5. Two schemas, and the code straddles them
`supabase/schema.sql` vs `supabase/migrations/0001_init.sql`

These describe different databases:

| | `schema.sql` | `migrations/0001_init.sql` |
|---|---|---|
| Votes | `voter_id`, `score INT 1-10`, `is_favorite` | `voter_user_id`, `value` enum, `favorite` |
| Attendance | table `attendance` | table `event_attendance` |
| Notes | table `notes` (`author_id`) | table `pnm_notes` (`author_user_id`) |
| Events | `date`, `type`, `is_active` | `starts_at`, `location`, `notes` |
| PNMs | `major NOT NULL`, `tags TEXT[]`, no email/phone | `email`, `phone`, tags via `pnm_tags` |
| Round type | `CHECK IN ('rush','dinner',…)` | `ENUM ('GENERAL','INVITE','BID')` |
| Roles | — | **both** `role_type ENUM('ADMIN','EXEC','BROTHER')` *and* `role text CHECK IN ('admin','member','observer')` in the same file (lines 12, 61) |

The backend queries tables from **both**. Concrete breakage:

- `GET /events/{id}/attendance` (`routes.py:1381`) and `GET /pnms/{id}/attendance` (`routes.py:1591`) read `FROM attendance` — a table the migrations never create. This is the check-in roster that Rush Mode polls every 5 seconds (`app/(dashboard)/rush/page.tsx:87`).
- `mark_attendance` writes to `event_attendance` **and then** to `attendance` (`services.py:1806`, `services.py:1825`). If `attendance` is absent the second insert raises *after* the first committed — the UI reports failure on a check-in that actually succeeded.
- `delete_pnm` deletes from `event_attendances` — plural, a typo, matching nothing (`services.py:1156`).
- `list_for_export`, which powers the PowerPoint export, reads `votes.score`, `votes.is_favorite` and the `notes` table (`services.py:1194-1220`) — all removed or renamed by migration `0005`. **The .pptx export will 500 on a migrated database.**
- `export_pnms_csv` also reads `FROM attendance` (`services.py:1866`).
- `_require_admin_or_exec` checks for role `"exec"` (`routes.py:481`) which the lowercase CHECK constraint cannot hold — so every bid-list route is admin-only in practice.

**Fix:** declare `supabase/migrations/` the single source of truth, delete or archive `schema.sql`, add a migration that drops the legacy `attendance` / `notes` tables, and rewrite every query that names them. Then remove the ~14 `try/except` schema-sniffing blocks in `routes.py` — they're hiding this class of bug, not solving it.

### B6. Logging in drops you on the marketing page
`frontend/app/login/page.tsx:76`, `frontend/app/(dashboard)/layout.tsx:142`, `frontend/middleware.ts:15-19`

When the marketing route group was added (`f4bfee6`), `/` became the public landing page. The dashboard lives at `/dashboard`. But:
- Login does `router.replace("/")` → user lands on the marketing site, logged in, with no way forward except typing a URL.
- The topbar and bottom-nav "Home" links both point at `/` (`layout.tsx:142`, `components/BottomNav.tsx:15`) → tapping Home inside the app exits the app.
- `middleware.ts` was meant to catch this — it redirects `/` to `/dashboard` when an `access_token` **cookie** exists. The app stores the token in `localStorage`, never a cookie, so the middleware is a permanent no-op. Its dashboard guard is dead for a second reason too: it matches `/dashboard*`, but the real routes are `/pnms`, `/rush`, `/events` — route groups don't appear in URLs.

**Fix:** point login and both Home links at `/dashboard`, and either make the middleware cookie-based for real or delete it so it stops implying protection it doesn't provide.

## 2. Features that are half-built

### 2.1 Live voting — the marketing claims outrun the code

The landing page says *"every brother sees the same PNM at the same time and their votes stream in over WebSockets."* Half of that is true. The chair's advance and lock **do** broadcast. Votes do not.

- **Live tallies don't exist.** `broadcast_vote_cast` is defined (`websocket.py:78`) and **never called**. `POST /votes` computes fresh tallies (`routes.py:1244-1262`) and returns them only to the voter who cast. The chair's "Votes Collected — 3 / 40" bar is set once when the session is created and never moves.
- **The lock is cosmetic.** `POST /sessions/{id}/lock` flips a boolean and broadcasts it, but `POST /votes` never checks `sessions.locked` (`routes.py:1140-1278`). A locked session still accepts votes. On the client, `disabled` is passed to the three buttons but not to the drag handler (`app/(dashboard)/voting/page.tsx:735-738`) — you can swipe-vote through a lock.
- **The timer is fake.** The UI collects "seconds per PNM" (`voting/page.tsx:528-535`) and sends `timer_seconds`; `POST /sessions` ignores it entirely. `GET /rounds/{id}/status` returns `"timer_remaining": 165` — a literal, with a `# TODO: implement timer logic` beside it (`routes.py:1654`).
- **"Anonymous votes" is fake.** Collected in the UI, ignored by the backend.
- **Favoriting before voting fails.** `handleFavorite` posts `{favorite: true}` with no `choice`; the backend rejects that with 400 *"choice is required for new votes"* unless a vote already exists (`routes.py:1204-1206`).
- **Any member can open a round.** `POST /rounds/open` only checks membership, not admin (`routes.py:1670`).
- **Rounds snapshot PNMs at creation.** A PNM added mid-rush never appears in an open round.
- `setIsChair(created.is_chair || true)` (`voting/page.tsx:320`) is always `true` — every user who starts a session is told they're the chair.

### 2.2 Bid list builder — a complete backend with no front door

`python_server/bid_list.py` is 327 lines of genuinely good work: create-from-round seeding by score, a 10-minute editor lock with takeover, bucket/position updates, finalize, CSV and PDF export. Twelve routes are wired (`routes.py:487-587`). There are ~30 passing unit tests across `test_bid_list.py` and `test_bid_list_routes.py`.

There is **no frontend**. `grep -rn "bid" frontend/` returns nothing. `@dnd-kit` is installed and unused — presumably staged for this. This is your single largest ratio of finished work to shipped value, and it's the feature a rush chair would actually pay for.

### 2.3 The entire admin surface is unreachable

`app/(dashboard)/layout.tsx:165-214` and `234-248` — the admin dropdown and the user menu items are commented out, with a pointer to `docs/archive/REIMPLEMENTATION.md`. What that orphans:

| Page | State | Reachable? |
|---|---|---|
| `/settings` | Working — chapter theme, questionnaire builder | ❌ no link |
| `/admin/users` | Working — roles, single + bulk email invites | ❌ only from `/settings` |
| `/admin/tags` | Working — full tag CRUD | ❌ only from `/settings` |
| `/analytics` | 1,029 lines, real | ❌ no link anywhere |
| `/admin/analytics` | **Duplicate of `/admin/users`** mislabeled "Analytics and Reports" | ❌ |
| `/profile` | Working | ❌ no link |
| `/compare` | Working, needs `?ids=` | ❌ nothing links to it |
| `/voting/admin` | Unstyled prototype; posts `type: "rush"` which the round enum rejects | ❌ |

The dashboard even toasts *"Invite your team from Settings"* (`dashboard/page.tsx:45`) — pointing at a page with no link and no invite UI on it.

### 2.4 Claims on the landing page with no implementation

- *"CSV upload or one-by-one"* (`HowItWorks.tsx:3`) — **there is no CSV import.** PNMs are added one at a time.
- *"Round management — explicit cutoffs and audit trails"* (`FeatureGrid.tsx`) — no cutoffs, no audit log.
- *"Chapter analytics — vote drift"* — `/analytics` exists but is unlinked and depends on the empty results endpoint.

Either build these or soften the copy before a chapter reads it.

### 2.5 Smaller gaps

- **No chapter switcher.** `getChapterId()` unconditionally takes `chapters[0]` (`lib/api.ts:113`) and caches it for 24h. Anyone in two chapters is stuck in whichever sorts first.
- **`lib/queries.ts` is mostly dead and mostly wrong.** Only the theme and fraternity-colors hooks are imported anywhere. The other fourteen point at endpoints that don't exist (`/pnms/{id}/comments`, `/chapters/{id}`, `/events/{id}`) or omit the required `chapter_id` query param (`useCreatePNM`, `useCreateEvent`, `useCreateTag`). Harmless today, a trap for the next person who reaches for them.
- **`/demo`, `/demo-topbar`, `/demo/signin`** are component playgrounds shipped in the production build.
- **`/intake` is a public URL that requires auth.** It calls `api("/chapters")` (`app/intake/page.tsx:36`), which 401s for a logged-out PNM, leaving `chapterId` null and the form permanently unsubmittable. It only works if a logged-in brother's token happens to be in that browser.
- **The events attendance export uses the wrong base URL.** `handleExportAttendance` builds `${NEXT_PUBLIC_API_BASE_URL}/events/export` raw (`events/page.tsx:270`), skipping the `/api` suffix that `getApiBase()` adds — 404 whenever the env var is set to the bare origin, which is what `api.ts` expects.

## 3. Frontend design audit — page by page

Two design systems are running side by side. Roughly half the app uses Subframe tokens (`text-heading-1 font-heading-1 text-default-font`); the other half uses raw Tailwind plus the legacy `beta-navy` / `beta-gray` aliases (`text-2xl font-bold text-beta-navy`). Neither is wrong; having both means headings are visually different sizes on Results vs PNMs, and no token change propagates cleanly.

### Global

| Issue | Where | Impact |
|---|---|---|
| **`font-serif` is undefined** — the entire marketing identity leans on it, but `tailwind.config.ts` never sets a `serif` family, so it falls back to Georgia/Times. The "editorial serif" look is unintentional. | `tailwind.config.ts:fontFamily`, all `components/marketing/*` | High — the landing page doesn't look designed |
| **A bogus font request.** `GoogleFonts.tsx:29` fetches `family=monospace`, which is not a Google font. That request 400s on every page load. Inter is loaded but never referenced. | `components/GoogleFonts.tsx` | Low, but noisy |
| **Fonts load via runtime `document.head` injection** instead of `next/font`, guaranteeing a flash of fallback text on every cold load. | `components/GoogleFonts.tsx` | Medium |
| **Pinch-zoom is disabled.** `maximumScale: 1, userScalable: false` | `app/layout.tsx:16-17` | WCAG 1.4.4 failure — and this is a mobile-first app |
| **Dark mode only exists inside the dashboard.** `ThemeProvider` is mounted in `(dashboard)/layout.tsx` only. A hard load of `/`, `/login`, `/get-started` or `/intake` in dark mode renders light. | `components/ThemeProvider.tsx` | Medium |
| **Theme applies in `useEffect`** with no blocking inline script → light-mode flash before dark paints, on every load. | same | Medium |
| **Dark mode is partly a hack.** `globals.css:164` force-overrides every `.bg-white` that lacks an explicit dark variant. It works until someone adds a card that *should* stay white. | `app/globals.css:162-171` | Medium — fragile |

### `/` — Marketing landing

The strongest visual work in the repo: the fanned hero cards, the draggable `SwipeDemo`, the rotated dossier cards. It reads as a real product. Then:

- **There is no header, and therefore no way to sign in.** `(marketing)/layout.tsx` renders `{children}` and a footer. No logo, no nav, no "Sign in". An existing customer landing on your homepage has no path to the app.
- **The footer text is invisible.** It uses `text-muted` (`MarketingFooter.tsx:14, 22, 78`). Tailwind resolves `muted` to its `DEFAULT`, `hsl(var(--muted))` = `43 30% 92%` — a near-white cream, on the `#FAF7F0` cream background. The tagline, all six links and the copyright are effectively unreadable. Everywhere else in the file tree the correct token, `text-muted-foreground`, is used.
- **Hover makes it worse:** `hover:text-accent-fg` → `#FFFFFF` on cream.
- **All six footer links are `href="#"`.** Features, Demo, Pricing, About, Blog, Contact.
- **The BID badge has no colour.** `SwipeDemo.tsx:41-42` uses `border-success` / `text-success`, but `success` is defined as a `50…900` scale with no `DEFAULT`, so those classes never generate. `danger` *is* a flat token, so PASS is red and BID is invisible — an asymmetry a viewer will notice immediately.
- **The star counter can never move.** `Decision` includes `"star"` and the tally renders it, but no control emits it.
- **Cards don't animate out.** They're wrapped in `AnimatePresence` with no `exit` variant; a swiped card vanishes.
- **Stale copy:** *"expanding to additional chapters in Fall 2026"* — that's now (`SocialProof.tsx`). And it names Beta Theta Pi at Cal Poly SLO two commits after `d9c5592 chore(brand): remove Beta Theta Pi references from UI`.

### `/login`
Clean and centred, but hardcodes `bg-neutral-50` / `bg-white` with no dark variants, has no link back to the marketing site or to `/get-started`, and shows the same fixed-width 384px card on every breakpoint. The password-reset branch is a near-duplicate of the sign-in branch — worth extracting.

### `/get-started` — Signup wizard
Functionally the most important page on the public site and visually the least finished: unstyled `<input>` elements with a bare `border-border` (the rest of the app uses `TextField`), a three-dot stepper with no labels, error text as a bare red line, no loading state on step 3. It also builds its API URL differently from every other call (`${NEXT_PUBLIC_API_BASE_URL}/api/v1/...`), which will produce `/api/api/v1/...` if the env var already carries `/api`.

### `/dashboard`
The best-composed page in the app. Active Event panel, onboarding checklist, clickable stat cards, a real mobile/desktop split for Quick Actions. Two notes: the third stat card spans two columns to fill a gap rather than because it's more important, and "Add PNM" appears in both the mobile pair *and* the More dropdown's sibling grid on desktop.

### `/rush`
Purpose-built for one hand at a rush event, and it shows — 48px targets, kiosk framing, sensible disabled states with an explanatory hint. Best UX page in the product. The native `<select>` for event choice is the one jarring element against an otherwise custom surface.

### `/pnms`
- **A four-column stat grid holding one card**, leaving three empty cells (`pnms/page.tsx:397-404`).
- **The search box refetches on every keystroke.** `loadPnms` is in a `useEffect` keyed on `search` with no debounce (line 112) — then the results are filtered client-side again anyway (line 145). The backend ignores the `search` param entirely, so the network round-trips accomplish nothing.
- **Multi-select exists but can't reach `/compare`.** You can select rows and bulk-tag, archive or delete — but there is no Compare button, and `/compare` is otherwise unreachable.
- **"Export → PowerPoint" shows for everyone**, then 403s for non-admins (`routes.py:922`).
- Two different "add a PNM" destinations: the header button goes to `/intake`, the empty state to `/rush`.
- Horizontal scroll at `min-w-[1200px]` with a sticky Actions column is a reasonable call, but on mobile it's a lot of table.

### `/voting`
Genuinely nice card design — full-bleed photo, gradient scrim, badge row. Undercut by the fake controls described in §2.1: a timer input that does nothing, an anonymity checkbox that does nothing, a lock you can swipe through, a "Votes Collected" bar that never moves, and a "Your Progress" panel that resets on refresh because it's local state.

### `/results`
Well-structured table with sort, filters, and status badges — rendering an empty array for every round (B3), and even once populated would show 0% / 0 / 0 because of B4. The `<thead>` is nested inside a `header` prop that likely already renders one.

### `/exports`
Clear card grid, good copy. But "Export Filtered PNMs" reads its filters from URL params that nothing ever sets — no page navigates to `/exports?tags=…`, so the button is permanently disabled. Same for the Comparison card. Header uses `text-2xl font-bold text-beta-navy` against the Subframe headings elsewhere.

### `/events`
The most feature-complete page after the dashboard: create/edit dialog, search, attendance counts, per-event check-in launch. `console.log` left in the load path (lines 92-104). Attendance export hits the wrong URL (§2.5).

### `/settings`, `/profile`, `/admin/*`, `/analytics`, `/compare`
All render fine; none are reachable (§2.3). `/admin/analytics` is a copy of `/admin/users` under the wrong title. `/voting/admin` is a raw prototype — unstyled checkboxes, `rounded-md border bg-white`, no design system — that should not ship.

### `/intake`
Two-step form with a progress bar, inline validation and a photo preview — solid. Requires a photo and a "Celebrity Crush" answer before it will submit, which is a lot of friction for someone standing at a rush table. And it 401s for the unauthenticated PNM it appears to be built for (§2.5).

## 4. What I'd build next

Ranked by *value to a rush chair per week of work*.

1. **Bid list UI** — the backend is done and tested. A drag-and-drop three-bucket board (Bid / Maybe / Cut) with the existing lock, plus the CSV and PDF exports already implemented. This is the "we made the decision and here's the artifact" moment, and no competitor's spreadsheet does it well.
2. **CSV / roster import** — every chapter already has a spreadsheet. Until they can paste it in, onboarding is an evening of typing. You already advertise this.
3. **Live vote tallies on the chair's screen** — call `broadcast_vote_cast`, which is already written. Watching "31 / 44 voted" tick up in real time is the single most demo-able thing in the product.
4. **Round cutoffs** — "advance the top N" / "cut below X%" from a results view, producing the next round. This is the actual workflow; right now rounds are flat and disconnected.
5. **A demo/sandbox chapter** — one seeded chapter with ~30 realistic PNMs, votes and events that any prospect can click into without signing up. You already have `create_demo_data.py` and `DEMO_PNMS`; wire them to a real read-only chapter. This directly serves your "demo to other fraternities" goal.
6. **Anonymous voting, properly** — the checkbox exists. Chapters care about this a lot; it's a common objection.
7. **Vote weighting for exec** — `votes.weight_applied` already exists in the schema (migration 0005) and is unused.
8. **Audit log** — who cut whom, who changed a role. Also advertised.
9. **PWA / offline check-in** — rush events happen in basements with no signal.
10. **Chapter switcher + a real onboarding invite flow** — the invite backend exists; it just needs a front door.

## 5. The plan

### Phase 0 — Establish ground truth (2–3 days)
Nothing else is trustworthy until this is done.

- [ ] Dump the production Supabase schema and diff it against `supabase/migrations/`. Confirm which of `attendance` / `event_attendance` and `notes` / `pnm_notes` actually exist.
- [ ] Delete or archive `supabase/schema.sql`; declare `migrations/` canonical. Update `CLAUDE.md`.
- [ ] Add migration `0013` to drop the legacy tables and reconcile the role model (pick lowercase `admin|exec|member|observer`, drop `role_type`).
- [ ] Add an integration test suite that runs against a real Postgres (docker service in CI) and hits every route once. The 81 existing tests are all mock-based — they cannot catch a missing table, which is why none of §1 was caught.
- [ ] Fix CI: it only triggers on `main`/`feat/**`/`fix/**`, never runs `npm run lint` (which is unconfigured and prompts interactively — `next lint` has no ESLint config), and never runs the frontend vitest suite.

## 6. So how far are you?

**~3–4 weeks** to a demo you'd be glad to give.

- **Phase 0 + 1 (≈1.5 weeks)** gets you to *"I can send a rush chair a link and they can use it."* That's the real threshold — everything before it is you doing manual SQL for every prospect.
- **Phase 2 (+1 week)** gets you to *"and the thing on the homepage actually happens."* Live voting is why they'll switch from a Google Sheet.
- **Phase 3 (+1 week)** gets you to *"and it produces the artifact chapter actually needs."*

Phases 4 and 5 are polish and can overlap. If you want a demo sooner, Phase 0 + 1 + a seeded demo chapter is a credible two-week version — you'd show Rush Mode, PNM dossiers, events and the PowerPoint export, and describe voting as shipping next month rather than demoing it broken.

### Two things worth doing this week regardless

1. **Get a real database in CI.** Every blocker in §1 except B4 and B6 is invisible to a mock-based test suite. You will keep rediscovering this class of bug until an integration test hits a real Postgres.
2. **Fix or soften the landing page.** CSV import, round cutoffs and audit trails are advertised and don't exist. A rush chair who tries the first one and finds nothing will not trust the rest of the list.
